## Model release lifecycle

`GET /v1/admin/model-releases` lists API-backed release-workflow resources; `GET /v1/admin/model-releases/{releaseId}` returns state and evidence.

| Action | Route | Result |
| --- | --- | --- |
| Create | `POST /v1/admin/model-releases` | `201`: staged release for `{ namespace, team, modelSlug }`. |
| Upload | `POST /v1/admin/model-releases/{releaseId}/upload-session` | `201`: upload URL for the declared SHA-256 and size. |
| Finalize | `POST /v1/admin/model-releases/{releaseId}/finalize-upload` | `200`: quarantined artifact metadata. |
| Validate | `POST /v1/admin/model-releases/{releaseId}/validate` | `202`: certification job queued. |
| Publish | `POST /v1/admin/model-releases/{releaseId}/publish` | `202`: registry publication queued. |
| Yank | `POST /v1/admin/model-releases/{releaseId}/yank` | `202`: serving blocked immediately; signed yank publication queued. |

These mutable workflow resources use IDs such as `rel_...`. They are distinct from the immutable `sha256:...` registry release identities used by serving authority and team grants.

An upload is not certification, and queued publication is not serving availability. Identity review, runtime certification, release approval, publication, current transparency verification, deployment, activation, loaded identity, routing, team authorization, accounting, and live inference are separate claims. Mutating release actions after create require `If-Match`; finalize, validate, publish, and yank also require `Idempotency-Key`. Read the returned release `etag` before the next mutation.

The current model-by-model evidence is listed on [Model assurance status](/docs/model-status). DeepSeek identity signatures do not create an API model row or authorize serving.

## Catalog & exact release identities

<Method method="GET" path="/v1/admin/models" returns="200" />

The response always contains registry catalog `models` and up to 1,000 newest `modelReleaseIdentities`. Pass `model={publicModelId}` to filter identities. When `team` is supplied, the response also contains retired `modelPolicies` and exact `modelReleaseGrants` for that team. Manifest and signature bodies are retained internally but never returned by this listing.

After a successful exact-identity sync, a catalog row points at an immutable registry `releaseId`: `sha256:<SHA-256 of the exact authenticated manifest bytes>`. Before that sync succeeds, a catalog row can omit `releaseId`; such a row is not grantable. Use the matching `modelReleaseIdentities` entry as the source of an exact release ID. Replacement manifest bytes produce a different release ID and never inherit an earlier grant.

| Field | Meaning |
| --- | --- |
| `id` / `backendModel` | Public model ID / verified serving alias. Clients send the public ID. |
| `releaseId` | Immutable exact-manifest identity used by deployment, activation, and grants. |
| `format` | `safetensors` for a native package, `gguf` for a GGUF artifact; historical identities may use an empty value, and catalog rows may omit it. |
| `runtime` | Signed engine/version, profile digest, context/output limits, reasoning capability, and memory hints. Native releases can also include optional `closureSha256` and `closureSizeBytes` for the runtime closure that contributes to `runtimeIdentitySha256`. |
| `certified` | The release/audit gate passed; this does not attest currently loaded runtime bytes. |
| `published` | The release is represented in the verified registry; this does not imply activation or availability. |
| `sigsumStatus` | Transparency state observed during registry verification, not a permanent live-health badge. |

Native safetensors use a `package.json` inventory, not a single GGUF file. Registry metadata remains distinct from deployment, activation, loaded identity, and protected routing.

## Legacy model-ID policies

<Method method="GET" path="/v1/admin/model-policies?team={team}" returns="200" />
<Method method="PUT" path="/v1/admin/model-policies" returns="200" />
<Method method="PATCH" path="/v1/admin/model-policies" returns="200" />

Migration 0020 retires model-ID-wide policies without backfilling authority. Existing rows remain audit history but cannot be created or re-enabled. A write must set `allowed: false`, must not set `isDefault: true`, and requires both the existing `If-Match` ETag and an `Idempotency-Key`.

## Exact release grants

<Method method="GET" path="/v1/admin/model-release-grants?team={team}" returns="200" />
<Method method="PUT" path="/v1/admin/model-release-grants" returns="200" />
<Method method="PATCH" path="/v1/admin/model-release-grants" returns="200" />

A grant authorizes one team and one immutable `sha256:...` registry release. Creating an allow grant succeeds only while the independently verified serving-authority snapshot contains that exact active release. A `412 precondition_failed` during allow-grant creation can therefore mean that the release is inactive or current serving authority is unavailable, not merely that an ETag is stale. Do not use the ETag reread/retry flow for that case: an operator must restore or provision authority for the exact release first. Revocation remains available during registry or serving-authority outages.

All grant writes require `Idempotency-Key`. Concurrency is conditional:

- omit `If-Match` when creating a row that does not exist;
- send the current grant ETag in `If-Match` when updating or revoking an existing row;
- an exact idempotent replay returns the original result;
- reusing the key with different parameters returns `409 idempotency_conflict`.

```bash
# RELEASE_ID is a sha256:... identity from /v1/admin/models, not a rel_... workflow ID.
curl -X PUT https://api.s46.dev/v1/admin/model-release-grants \
  -H "Authorization: Bearer $S46_ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: grant-$(uuidgen)" \
  -d "{\"team\":\"@s46/engineering\",\"releaseId\":\"$RELEASE_ID\",\"allowed\":true}"
```

Saving a grant does not manufacture publication, deployment, activation, loaded identity, route health, or capacity. Read effective production authorization from authenticated gateway discovery. The team response's model fields are compatibility data and do not reflect exact grants.

## Serving-authority inspection

<Method method="GET" path="/v1/admin/serving-authority" returns="200 / 503" />
<EndpointMeta>Auth · **configured operator token**</EndpointMeta>

This read-only route returns non-secret current `releaseId`, `modelId`, deployment, activation, loaded-identity, route and instance IDs, plus activation and loaded-identity expiry times. Tenant owner/admin tokens do not authorize it. Use `Authorization: Bearer <operator-token>` or `X-S46-Admin-Token`; a supplied bearer credential takes precedence.

There is no API route for submitting, signing, or weakening activation evidence. A `503 serving_authority_unavailable` response means the current authority chain cannot be inspected as valid. See [Serving authority](/docs/serving-authority) for the client-visible gate.
